Guide — what each option does

Global bar

Consists — how many 6-Teiler are coupled (1–3). Backbone trunk — RSTP port cost of every internal e0-0/e0-1 hop; VDS long path-cost table: 10G=2000 · 1G=20000 · 100M FE=200000. B1–B3 chord — the deliberately high cost (template 400100) on the B-car ring chord so the solo train's ring always breaks there, predictably. Max age — BPDU lifetime: a BPDU dies after (max-age − 1) hops from root; template default was 20, v9 raises it to 38.

v9 · 20000 preset — flat symmetric cost on all coupler e0-2 ports, both trains. The storm-safe fix, field-validated 2026-06-30.

v8 formula preset — the old template rule: A1 & B3 e0-2 cost = Fzg × 1,000,000 − 1 (Fzg 145 → 144,999,999) while A3 & B1 stay at the trunk default. Each train computes the value from its own Fzg, so when two trains couple, the two ends of the live cable carry different costs → a never-settling designated-role duel → ~2 s fleet-wide TC/FDB-flush storm (field-proven 2026-06-12; cold coupled boot with this config failed to converge at all on 2026-06-30).

Train cards

Fzg — customer train number; only feeds the v8 preset formula. D1 priority — RSTP bridge priority of that train's D1 (the root candidate). Lower wins root; equal priorities fall through to lowest MAC — in this sim MAC order is T1 < T2 < T3, so set one D1 lower to pin the root deliberately. A ⟶ B — turns the train around so the other end faces the Kupplung; use it to build all four orientations (A-A, B-B, A-B, B-A). Coupler e0-2 costs — per-port cost of the four Frontkupplung ports.

Kupplung cards

Each junction has two redundant cables. Untick one to model a missing/failed cable (the 2026-06-30 field test coupled with only one live). Pairing — straight (port 1↔1, 3↔3) vs crossed (1↔3) models how the physical cables landed.

Verdict — can one redundant coupler cable be deterministically blocked?

Yes, the meeting is right that symmetric coupler cost does not deterministically block one redundant coupler cable — but the validated simulation (ground-truthed against the 2026-06-12 and 2026-06-30 live harvests, then adversarially attacked) sharpened why, and that changes what to do about it:

1 · It's not a coin-flip — it's deterministic per case, but the case depends on orientation AND root position.
Driven by each train's fixed backbone distances from D1 to its coupler ports (A1/A3/B1/B3 = 4000/6000/22000/12000) plus cost-tie resolution by bridge MAC. Sim-verified across all 8 orientation × root combinations (both cables live): a standby coupler exists in only 3 of 8 — everywhere else both cables forward and the loop breaks on internal links instead.

And since root election is itself a MAC lottery today (equal priority-0 D1s), the "working" orientations cannot even be enumerated absolutely — the same physical coupling flips outcome class when the other train wins root. Fleet limitation: treat "standby coupler exists" as not guaranteed under v9.
2 · The implied fix — asymmetric coupler cost — is doubly wrong.
Sim-proven it cannot deliver orientation-invariance (3 distinct outcome classes across 4 orientations), and it reintroduces the storm: the designated-role duel was proven twice on live trains, and a cold coupled boot with asymmetric costs failed to converge at all (2026-06-30).
3 · No static config knob can fix it.
root_path_cost dominates the RSTP priority vector with wide margins at every coupler comparison, so port-priority is structurally never even read; bridge-priority only breaks ties, not costs. Candidates A (asymmetric cost), B (port-priority), C (bridge-priority) and static-D all produced byte-identical sim output across all four orientations — a value fixed at commission time cannot know the orientation that will occur in the field.
4 · The solution is a control-plane action, not an RSTP knob.
Solution: a CCU application that reads the multitraction state from the Stadler DXS (the train control system knows coupled state and master/slave role) and deterministically admin-disables the designated spare Frontkupplung switch port — equivalent to unplugging the spare before RSTP computes, which sidesteps the cost arithmetic entirely. Static config cannot do this: OBN templates render once at commission time, before any coupling event. Design requirements (adversarially verified in the sim): failback — continuous link monitoring with re-enable, so a later fault on the surviving cable fails over to the spare instead of severing the consists; root alignment — tie bridge priority / root election to the same DXS master/slave signal so the kept cable is also the best path; per-junction scope — "disable my spare" must mean "per facing neighbour", so a middle consist in triple traction disables one spare per junction, not every coupler port but one.
