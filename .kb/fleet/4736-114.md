# The misimage collision (resolved 2026-06-20)

- **Symptom:** the 4736-114 CCU had been imaged as **T17 / 10.179.17.1** — that is **4706-103's**
  identity. Both the real 4706-103 and this misimaged CCU claimed `10.179.17.1`. 4706-103 won the
  collision (healthy `6017` in Zabbix); 4736-114 lost → couldn't reach/ping Puppet and was absent
  from NMS/Zabbix.
- **How identity was proven:** SIM ICCIDs matched 4706-103's protocol; **IMEI in NMS settled it**
  (modem-hardware-bound, cannot be misimaged — 6017 reported 103's IMEI, so 6017 IS the real 103);
  114's own identity confirmed over **console** (out-of-band) showing T17/10.179.17.1.
- **Fix:** re-addressed the CCU to end the collision and set train_id template to Fzg 142; folded
  into one chroot promote + reboot. Verified live: on `10.179.27.1`, not answering on `10.179.17.x`,
  103/6017 undisturbed, **zero 10.179.17/103/6017 contamination** in `/etc/nd-backbone` or `/etc/obn`.
- **Prediction correction:** the earlier note predicted the fix would land on `10.178.27.1` (178).
  It landed on **`10.179.27.1`** (179). Don't re-litigate the second octet.

# Proven dead ends

- Do **not** infer CCU identity from config/subnet alone when a collision is suspected — config can
  be misimaged. Use IMEI (NMS) or console; both are identity-independent.
- Fixing train_id alone and rebooting is a **trap** — it leaves the CCU on `10.179.17.1` → re-enters
  the collision → still no Puppet. The IP re-address is what ends the standoff.
