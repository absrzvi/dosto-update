## Findings

### 1. The "m-variant can't partition-swap" theory is WRONG
Both buckets contain m AND non-m APs. Successes: .218m, .219m, .223m, .227m (m) + .229, .232 (non-m). Failures: .220, .221, .224, .226, .233 (non-m) + .222m, .228m, .230m, .231m (m). **The split is not variant-related.** The single Ibex image transfers to all APs; failure is not image-availability. Supersedes the old `project_m_variant_ap_fw_activation_fail` memory note.

### 2. Batch mode WORKS with the TFTP helper — but is slow & partial
6/16 flashed in one batch pass (vs 0 on 2026-06-02 and 0-confirmed on Fzg 143). The conntrack helper unblocked the data path. But only 6/16 in one pass → the other 10 likely need a **second batch pass** (16 concurrent TFTP transfers starve some; this is the expected batched-TFTP contention pattern). Re-running `obn update f ap` should pick up the remaining 10.

### 3. Bug 11 has TWO defects this run exposed (R&D — TRIAG-8585)
The log verdict did NOT match discover ground truth:
- **False failures:** .227, .229, .223, .219, .232 logged "RT-610 hang / did NOT complete within 600s" but **all actually activated** (uptimes 2–5 min — they rebooted *after* the 600s poll window closed). **The 600s timeout is too short under 16-way concurrent batch load.**
- **False pass:** .220 logged clean (no error) but is **still 6.10.0-0** — did not activate.
- **Misleading message:** line 143 hardcodes `"RT-610 flash-trigger hang"`. These are **Ibex** APs. The attribution is wrong; the message should not name a hardware model it didn't verify.
- **Note:** the `[+] <ip>: firmware update applied, device rebooting.` print fires unconditionally even on the error path — unreliable, should be gated on the actual verdict.

### Bug 11 R&D action items
1. Increase / make-configurable the activation poll timeout (600s insufficient for batch).
2. Remove the hardcoded "RT-610" attribution; report only the observed `rpcFwFlash` value + actual `hardware_revision`.
3. Gate the "device rebooting" success print on the real verdict, not unconditionally.
4. Consider: poll should re-check firmware version post-window before declaring failure (catches late activations).

## ROOT CAUSE OF THE FIRST-PASS FAILURES (captured before retry — would have been erased)

Stabilized final count: **7 activated (IbexOS 6.11.2-0) / 9 failed** (.220 .222 .224 .225 .226 .228 .230 .231 .233, all ~90min uptime, never rebooted, still report "RT SW6 Firmware - 6.10.0-0").

**Live `rpcFwFlash` (OID .1.3.6.1.4.1.16177.1.400.1.3.2.1.0) on the 9 failed APs = `-1` (downloadError) on ALL 9.** Control: activated APs .218/.227 = `0` (nop/done).

`-1` = **downloadError**, NOT `2` (writing/hang). So these did NOT hit the genuine RT-610 flash-trigger hang (that case sits at `2` with multi-hour uptime, seen on 4736-109). **These APs failed to DOWNLOAD the image** — the TFTP transfer failed.

**tftpd confirms the mechanism:** `in.tftpd: tftpd: read(ack): Connection refused` ×9 at 06:20. The AP→CCU TFTP return path got ICMP port-unreachable = the conntrack/NAT return mapping for that AP's TFTP session was absent when the AP ACK'd. **This is the conntrack-helper-under-concurrency failure: the helper IS loaded, but 16 simultaneous TFTP flows racing through it overran clean tracking → ~9/16 downloads refused → downloadError(-1).** The batch version of the exact gap the helper was meant to fix.

### CORRECTED root cause (supersedes the "RT-610 hang" reading earlier in this file and in mid-session notes)
- First-pass failure here = **TFTP download failure under 16-way batch concurrency**, NOT a flash-trigger hang and NOT m-variant. The "RT SW6 Firmware" in sysDescr is just the pre-flash firmware NAME, not evidence of a hardware-hang.
- This is RECOVERABLE by retry (fewer concurrent flows) or serial push — there's nothing wrong with these APs.
- The genuine-hang case (rpcFwFlash=2, never reboots, hours of uptime) from 4736-109 is a DIFFERENT failure. Two distinct failure modes now documented: (A) download-refused-under-batch (rpcFwFlash=-1, this run) vs (B) genuine flash-trigger hang (rpcFwFlash=2, 4736-109).

### R&D implication (TRIAG-8585)
Batch `obn update f ap` is unsafe at full fan-out — the TFTP conntrack helper doesn't reliably track 16 concurrent flows. Options: (1) throttle OBN's AP-fw concurrency (e.g. 4-at-a-time), (2) harden the conntrack helper / raise nf_conntrack limits, (3) keep single-AP serial as the safe default. Bug 11's verdict was ALSO unreliable here for a separate reason (600s window too short → false-failed late activations) — but that's orthogonal to the download failure.

## PASS 2 (retry) RESULT — TWO STACKED FAILURES, now separated

Final count UNCHANGED: **7 at 6.11.2-0 / 9 at 6.10.0-0.** Retry did NOT recover the 9.

| Layer | Pass 1 (16-way) | Pass 2 (lower contention) | Verdict |
|---|---|---|---|
| TFTP **download** | ❌ 9× `Connection refused`, rpcFwFlash=`-1` (downloadError) | ✅ 0 refused, the 9 moved `-1`→`2` (delivered) | **Concurrency-caused — FIXABLE** |
| Flash **commit/activation** | (masked by download fail) | ❌ all 9 stuck `rpcFwFlash=2`, uptime ~2h00m, **never rebooted** | **Genuine RT-610 flash-trigger hang — NOT concurrency** |

So this AP set had TWO independent failures stacked. Pass 2 proved the download layer is concurrency-driven and recoverable (0 refused, -1→2). But underneath, 9/16 APs have the **genuine flash-trigger hang** (the 4736-109 `rpcFwFlash=2`/never-reboot signature): they accept the image, ACK the flash, then sit in "writing" forever. These will NOT activate over the SNMP path regardless of TFTP optimization. NB: unlike 4736-109's "flaky" trigger, a full retry did NOT shake these 9 loose → leans "dead" not "flaky" for this consist. Real activation needs the LuCI HTTPS upload bypass or a Westermo firmware fix.

Bug 11 ENDED UP CORRECT on pass 2: with the download succeeding, it will (after its poll window) honestly report these 9 as failed (stuck at 2, no reboot) — which is the true state. Its pass-1 verdict was wrong only because the underlying failure was download, not flash.

## TFTP BATCH OPTIMIZATION — so a full batch doesn't need redoing

Root cause of the download failures (confirmed): `update.py:328` does `ThreadPoolExecutor(max_workers=len(devices))` — **unbounded fan-out**; all APs are leaves so the whole consist is ONE batch → 16 simultaneous 100MB TFTP pulls. Live limits showed it's NOT table exhaustion (`nf_conntrack_count=828 / max=262144`) — it's **UDP-timeout expiry under contention**: `nf_conntrack_udp_timeout=30s` expires the helper's return-path expectation during mid-transfer gaps → AP's next packet has no return mapping → ICMP port-unreachable → `read(ack): Connection refused`.

### Tier 1 — cap OBN's worker pool (real upstream fix → TRIAG-8585)
`update.py:328`: `max_workers=min(4, len(devices))` (was `len(devices)`). 4 concurrent transfers fit the helper cleanly; whole consist completes in ONE invocation, no retry. Better: make it config key `firmware_max_workers`. Requires R&D release.

### Tier 2 — widen conntrack UDP timeout (CCU-side, runtime-tunable, APPLIED 2026-06-09)
```
sysctl -w net.netfilter.nf_conntrack_udp_timeout=180        # was 30
sysctl -w net.netfilter.nf_conntrack_udp_timeout_stream=600 # was 120
```
Stops entries expiring mid-transfer. **Applied live on box1-t54 this session (runtime-only, wipes on reboot).** Persistent home = Puppet `60-allow-management` alongside the conntrack-helper rule (same gap tracked in TFTP-helper note). Validation of a clean 16/16-in-one-pass run is DEFERRED — pass 2 was already in flight when applied, and the remaining 9 are blocked by the *flash-hang* layer, not download, so this consist can't demonstrate it. Validate on a fresh train whose APs don't have the hardware hang.

### Tier 3 — operational, zero-code (the current playbook default)
Chunk pushes to ~4 APs at a time, or single-AP serial (`dosto-ap-firmware-update`). This is exactly what CLAUDE.md handoff-lesson-11 already mandates ("never re-introduce parallel batches for obn update f without evidence the TFTP-helper gap is fixed in Puppet"). **This test is the hard evidence for WHY that rule exists** — measured mechanism (conntrack UDP-timeout expiry at 16-way fan-out) + quantified (7/16 pass1, 9 downloadError, 0 refused on lower-concurrency retry).

### Recommendation
Tier 2 → Puppet (durable CCU fix, makes even unbounded OBN survive). Tier 1 → R&D (clean upstream). Tier 3 stays the safe default until either lands. None of these help the 9 flash-hung APs here — those are a separate hardware-trigger problem (LuCI bypass / Westermo fix).
