**2. vlan7 formula fix (DevOps, Puppet)**

The CCU vlan7 IP (transit link to the Stadler firewall) is generated by a broken formula in `nd_redundancy/networks.epp`. Confirmed on the `migration/mar5` branch it's still:
```
ipaddress: "172.19.{{ 128 + ((fis_id + train_id) // 2) }}.2"       # even
ipaddress: "172.19.{{ 128 + ((fis_id + train_id - 1) // 2) }}.130" # odd
```
The `fis_id` term is a leftover bridge from the old box-id ≠ Fzg model. Once we re-IP so `train_id` = Fzg, drop it so vlan7 derives directly from `train_id`:
```
ipaddress: "172.19.{{ 128 + (train_id // 2) }}.2"       # even
ipaddress: "172.19.{{ 128 + ((train_id - 1) // 2) }}.130" # odd
```
Two notes for the same MR:
1. Order matters — this fix is only correct *after* a train is re-IP'd (it depends on `train_id` = Fzg). Roll it out with the re-IP per train, not ahead of it.
2. Keep the host octet `.2` (even) / `.130` (odd) — the CCU's designated vlan7 address (Stadler FW is `.1`).

Everything else in `networks.epp` already derives from `train_id` and renders correctly once `train_id` = Fzg, so this one term is the only vlan7 change the migration needs.

**3. NMS train records + Zabbix (DevOps)**

The re-IP changes each CCU's `rtl_train_id` from `6000+box-id` to `6000+Fzg`. Zabbix hosts (`50_6<id>_<role>`) are auto-generated by NMS, and the internal/RTL train-ID cannot be edited on an existing NMS record — so each migrated train has to be **removed and re-created in NMS** to regenerate its hosts against the new ID and CCU IPs. Renaming in Zabbix alone won't hold.

1. Old `50_6<box>_*` Zabbix hosts are orphaned on recreation and need cleanup.
2. `rtl_project_id` stays 50 for the whole fleet (4734 and 6-car) — must not change (a 51 here makes the train dark in NMS).
3. Post-check each recreated train lands in the project-50 monitored set, not just the train list.
4. Expect an ICMP/SNMP alarm flood per train window from stale IPs — plan a trigger-window bump.

This is 50 train recreations in NMS — DevOps effort to size alongside the re-IP.

**5. Fix fv5/fv6 `obn report` — config, not version (DevOps, Puppet)**

`obn report` is broken on some fv5/fv6 trains, but this is a **`backbone-discovery.yaml` config problem, not a package version.** OBN selects its report class from the `report_module` config key. DOSTO must use `report_module: DostoNeuReport` (which has self-contained nv4/nv6/fv5/fv6 support since nd-obn 2.2.24, RD-11895, and is still present in 2.3.6). If `report_module` is left at the package default `GenericReport`, the report routes to a topology-driven engine that has no DOSTO topology → it fails.

Verified 2026-07-02 across three live CCUs — this is per-train config drift:
- box1-t42 (fv5): `train_type: mq` + `report_module: GenericReport` (both package defaults) → report fully broken.
- box1-t41 (fv5): `report_module: DostoNeuReport` (correct) but `train_type: nv4` (wrong — should be fv5) → wrong consist shape.
- box1-t50 (nv4): both correct.

Fix (per train): set `backbone-discovery.yaml` to `report_module: DostoNeuReport` + the correct `train_type` (nv4/nv6/fv5/fv6), and make the Puppet template enforce both so they can't fall back to the `mq`/`GenericReport` defaults on reimage/upgrade. No package bump needed — DOSTO works on 2.2.23 with correct config. (Note: this supersedes the earlier "bump to 2.3.6" theory — the version was a red herring.)

**FZG-ID vs Train-ID — the decision behind the re-IP**

Stadler give us a Fzg ID per train, which drives the switch config (IP-address formula). OBN generates configs from our Nomad train-ID (box-id), which is different from the Fzg ID — so today we hand-edit `/etc/obn/template/*.cfg` on every train to overwrite the train-ID with the Fzg. That hand-fix is wiped by the next `obn update c`, and the same root cause leaves NTP generating a wrong IP.

There is a clean formula, but it maps the customer Train# (e.g. 4736-104) to the Fzg — not our box-id to the Fzg. OBN only ever sees the box-id, and box-id↔Fzg is a scrambled lookup with no arithmetic relationship (verified: all IPA PDFs match the design-freeze sheet, and the box-ids are genuinely out of order). So no formula OBN can evaluate at render time will produce the Fzg.

My recommendation is to set box-id = Fzg by running `factory up` on all trains with the Fzg as the train-ID. This makes `train_id` = Fzg everywhere, so no template hand-edit, no `fzg_id` key, no OBN engine change, and it fixes NTP and vlan7 (item 2). Cost is roughly 1 month of additional PE hours to recommission the fleet.
