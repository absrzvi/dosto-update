## Key lessons discovered this session

### 1. OBN canonical workflow: `discover → report → update/validate`

OBN is designed so that `obn update c` and `obn validate` read from `discovery.prev.json` (the committed report snapshot), not `discovery.json` (the raw scan). `obn report` is what commits the scan into that snapshot. This is intentional — it ensures OBN operates on a stable, audited view of the network, not a live scan.

**Always run this sequence before any `obn update` or `obn validate`:**
```bash
sudo obn discover   # writes /tmp/discovery.json (raw scan)
sudo obn report     # commits it to /tmp/discovery.prev.json (stable snapshot)
# Now obn update c <ip> and obn validate will see all 43 devices
```

Skipping `obn report` causes: (a) "Update not supported for readonly devices" — stale/empty prev.json → empty device set → Python `all([]) = True`; (b) `obn validate` empty table.

### 2. `obn validate` returns empty table when consist.yaml is empty

`consist.yaml` on box1-t47 was empty (OBN hadn't built a topology tree). `obn validate -t sw` returned headers but no rows. Workaround: read `/tmp/discovery.json` directly via Python to enumerate devices and their config/firmware state.

### 3. `08_e2e_probe.sh` had hardcoded FW IP `172.19.196.1`

The `dosto-l2-health` skill script `scripts/08_e2e_probe.sh` had a hardcoded default second argument `FW_IP="${2:-172.19.196.1}"`. For Fzg 130 whose FW is at `172.19.193.1`, this produced a false `path_broken` result. Workaround: always pass the second argument explicitly: `bash 08_e2e_probe.sh <ccu-ip> <fw-ip>`. A background task was spawned to fix the script to derive FW IP from the CCU's live vlan7 address automatically.

### 4. Stadler FW commission state: ICMP loss = commissioned (not a fault)

Confirmed again on Fzg 130: `ping -c 5 172.19.193.1` returned 100% loss with ARP REACHABLE. This is the expected commissioned state — Stadler policy drops echo-request. The 2026-05-11 journal entry left this open; now confirmed closed.

### 5. `all()` of empty iterable in Python = True

Python's `all([])` returns `True`. This is standard Python semantics but it's the exact footgun in `update.py` line 273 that causes the false "readonly" warning when the device list is empty. Worth noting for future OBN debugging.

### 6. VDS switch reboot command unknown

We attempted to SSH into switches to trigger a reboot during investigation. Tried: `reboot`, `reload`, `system reboot`, `system restart`, `reload system`, `do reboot` — all rejected with *"Error in command, param is X [wrong]"*. `show version` works fine. The correct VDS switch CLI reboot command is not documented in the switch manual extract — check `docs/switch_user_manual.pdf` for the full CLI command reference, or ask Stadler.

### Root cause of the no-op (the catch-22)

Traced through `cli/update.py::update()`:
1. `get_devices(report_file)` ✓ — reads 43 devices from prev.json.
2. `get_targeted_devices(devices, target=('10.179.47.180',))` ✓ — finds .180.

`Device.needs_configuration_update()` in `lib/report/device.py:67`:
```python
def needs_configuration_update(self) -> bool:
    if self.target is None or "config" not in self.target:
        return False
    return bool(self.config) and not self.config.endswith(self.target["config"])
```

We verified via the loader:
```
10.179.47.180  config: nv6-E1-v5-man  target: None  needs_config_update: False
```

**`target` is None on every device in `discovery.json` / our copied `prev.json`** — the `target` field is populated by OBN's rules engine driven from `/etc/obn/rules.yaml`, and that runs inside `obn report` (specifically in `number_coaches()` / `apply_rules` after coach-numbering). **The dependency chain:**
```

```

## Session 2 part 2 — root cause located: duplicate switch hostnames

After writing the catch-22 note above, kept debugging. **Real root cause is not the 3 `-man` switches alone — it's that the consist has duplicate switch positions.**

### Found the infinite loop

`number_coaches()` in `/usr/share/obn/lib/report/report_dosto_neu.py` is a BFS of the LLDP neighbour graph. The bug is at lines 281–282:

```python
                # Add to_device to queue
                queue.appendleft(to_device)
                continue
```

This `appendleft` is **unconditional** — it adds the neighbour to the queue regardless of whether any rule assigned `coach_number`. Combined with the guard at line 47 (`if to_device.coach_number is not None: continue`), this means: if a neighbour fails to receive a `coach_number` this round AND its own neighbours also haven't been numbered yet, the device gets re-queued forever, ping-ponging until something else terminates it (timeout, SIGKILL).

Confirmed via watchdog + SIGALRM stack trace: program was stuck in `for neighbour in from_device.neighbours:` at line 42.

### Why we halted — STP-root anomaly

Before pushing, we queried STP state on `.188`, `.186`, `.178`, `.192`:

- **STP root bridge: `32768/a0:59:3a:d0:28:00` = `.192`** (currently labelled B3-v5-130, in the "unreached" top chain).
- `.188`'s root port is **e0-0**, cost 2000 — but the B3 template assigns `spanning-tree port-cost 400100` to e0-0 (backup) and default cost to e0-1 (preferred). Observed STP behaviour is *opposite* to template intent.
- `.188.e0-0 → .178` per LLDP, but B3 template description for e0-0 says "Switch B1". `.178` is currently labelled B2.
- `.186 (B1)` reaches root via e0-0, path cost 6000 (3 hops × 2000). Its e0-0 → `.188`.

### What this means

Three possibilities:

(α) **Cabling fault** — Stadler swapped cables on `.188`, OR `.178`/`.186` labels are swapped relative to physical position, OR a deeper swap higher up the chain.

(β) **STP priority not set** — the per-position templates may set lower bridge priorities on certain switches (e.g. D-coach SWs) to make them root. `.192` becoming root by default suggests no priority was configured, so it won the election by having the lowest MAC. Pushing v8 to D1/D2/D3 first might cure this.

(γ) **Both** — cabling fault AND mis-imaged switches compounding.

### Why we did NOT push v8 to .188

The B3 template's port-cost asymmetry means a wrong-direction push would either:
- Force the root path off a working link, OR
- Create an STP topology change (TCN) that flushes MAC tables for ~30s across the consist, potentially knocking out customer-impacting flows.

Without physical verification of which cable goes where, **any push to .188 risks a transient outage we can't predict.**
