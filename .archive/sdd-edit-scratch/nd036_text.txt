Nach Konvention werden CCUs von der niedrigsten Nummer zur höchsten Nummer bestellt, basierend auf Die CCU sendet und empfängt Multicast-Nachrichten mit: Redundancy uses multicast to discover other CCUs in the consist and update the configuration accordingly. By convention CCUs are ordered from lowest number to highest number, based on The CCU sends and receives multicast messages with project ID Projekt-ID Zug-ID Geräte-ID train ID unit ID This enables each CCU to know how many CCUs there are in the consist and the CCU with the lowest ID (decided in the above order) will become the master CCU running the DHCP service . At Startup time ND-Redundancy waits 30 seconds to discover other CCU`s if present, before taking actions. Multicast messages are sent every interval (default 10s) and another CCU in the consist is considered dead after it has failed sending messages for 3 intervals in a row. Recovery is done immediately after multicast message is received from the second CCU. In a Split-brain-scenario the two or more CCU`s do a recovery when they receive each other’s multicast messages. Dies ermöglicht es jeder CCU zu wissen, wie viele CCUs es in der Zusammenstellung gibt, und die CCU mit der niedrigsten ID (entschieden in der oben genannten Reihenfolge) wird die Master-CCU, die den DHCP-Dienst ausführt. Zur Startzeit wartet die ND-Redundanz 30 Sekunden, um andere CCUs zu entdecken, falls vorhanden, bevor Maßnahmen ergriffen werden. Multicast-Nachrichten werden alle Intervalle (standardmäßig 10s) gesendet, und eine andere CCU in der Zusammenstellung gilt als tot, nachdem sie 3 Intervalle hintereinander keine Nachrichten gesendet hat. Die Wiederherstellung erfolgt sofort, nachdem eine Multicast-Nachricht von der zweiten CCU empfangen wurde. In einem Split-Brain-Szenario führen die zwei oder mehr CCUs eine Wiederherstellung durch, wenn sie die Multicast-Nachrichten des jeweils anderen erhalten. Discovery-Phase: Während der Discovery-Phase von OBN verwendet die Anwendung das LLDP-Protokoll, um eine Karte des On-Train-Netzwerks zu erstellen. Dieser Prozess beginnt bei der CCU. Die Anwendung springt von Switch zu Switch, von Switch zu Access Point und erstellt eine interne Topologie der Art und Weise, wie das Netzwerk aufgebaut ist. LLDP macht die Nachbarn sichtbar, die die CCU, ein Switch oder ein Access Point sein können, wodurch OBN von einem Knoten zum nächsten springt und sich langsam über das gesamte Netzwerk verzweigen kann. Unterwegs sammelt OBN Daten wie IP-Adressen, MAC-Adressen, Gerätetyp, Firmware-Version, Konfigurationsversion usw. Um dies zu erreichen, müssen die Netzwerkkomponenten einen Mindestsatz an Funktionen implementieren, z. B. die Möglichkeit, die LLDP-Nachbarn über ein Protokoll wie SNMP oder SSH zu erkennen. Da jedes Gerät über einen anderen Satz von SNMP-OIDs verfügt, die diese Art der Erkennung ermöglichen, ist es für OBN auch wichtig zu wissen, mit welcher Art von Gerät es kommuniziert. Dies erfolgt basierend auf dem MAC-Präfix. Intern speichert OBN eine Liste bekannter Geräte zusammen mit ihren bekannten MAC-Präfixen, sodass OBN entscheiden kann, wie das Gerät abgefragt werden soll. Das Ergebnis der Discovery-Phase wird im File /tmp/discovery.json gespeichert. Reporting-Phase: Die Reporting-Phase von OBN verwendet die Ausgabe der vorherigen Discovery-Phase und übersetzt sie in ein tatsächliches Layout. Der anfängliche Discovery-Prozess kennt Werte wie die Waggonnummerierung nicht - erst in dieser Phase wird die Ausgabe in eine reale Karte des Zuges übersetzt. Diese Karte kann anschließend entweder vom NMS oder für die Konfigurationsphase verwendet werden. Die Reporting-Phase versucht, die erkannten Backbone-Daten dem erwarteten Konsistenzlayout zuzuordnen, das in einer Konfigurationsdatei definiert ist. Diese Konfigurationsdatei definiert genau, was in einem Zug zu erwarten ist: die Anzahl der Waggons, die Anzahl der Switches und Access-Points pro Waggon, wie sie miteinander verbunden sind usw. Dieses Layout der Konfigurationsdatei wird mit dem entdeckten Layout verglichen. Konfiguration des Stromversorgungskreises: Configuration of the power supply circuit: Die R5001C CCU sollte gemäß der folgenden Beschreibung mit dem Fahrzeugbatterie- / Stromversorgungskreis verbunden werden. Dauerhafte Batterieversorgung der CCU-Stromeingabe und Leistungssteuerung über das Zündsignal (ignition signal). Wenn das Zündsignal angelegt ist und die Bedingungen für den Start der CCU erfüllt sind, startet die Einheit nach einer kurzen Verzögerung von 35 Sekunden. Die kurze Hochfahrverzögerung stellt sicher, dass das Fahrzeug-Stromversorgungssystem stabilisiert ist, bevor die CCU gestartet wird. Wenn das Zündsignal entfernt wird, wird die CCU für eine programmierte Anzahl von Minuten [1, 4, 10, 15 Minuten, Standard = 4 Minuten] weiterbetrieben und führt dann einen sanften Abschaltvorgang durch. Eine solche Funktionalität bietet folgende Vorteile: The R 5001C CCU should be connected to the Vehicle Battery / Power Supply circuit as per following description. Permanent battery supply connection to the CCU power input, and Power control via the Ignition signal input. When the Ignition signal is applied and the conditions to start the CCU are fulfilled, the unit boot s up after a short delay of 35sec. The short boot up delay ensures that the Vehicle Power supply system has stabilised before the CCU is started. PM-13: RTPI / OBN Konfiguration (Verifikation Dynamischer Inhalt) RTPI (Real Time Passenger information) delivers journey and train consist information to Nomad’s products such as NMS, OBIS, Engage Portal, and Fleetview. This makes RTPI an important part of delivery specially in cases of a dynamic consist . The high level design of the standard Nomad RTPI platform is provided below: • Journey Ingestion Service: This is the part that receives data from a client journey feed service. It contains the customer bespoke logic to convert data into the standard format. It converts customer data into JSON format so that RTPI Database importer can save it in the database. • RTPI Database Importer : This component consumes the JSON file and imports it into the RTPI database. It is a product component and does not need to change between projects. • RTPI Publisher: This reads the data from the database and publishes it on HIVE. The information is being published on every change in the database . • RTPI WebApi: RTPI exposes information on API too. This API provides latest journey information such as downline stations, ETA etc. • RTPI Static file importer: Journey Ingestion service does not always provide the complete data such as station names, geo-fences etc. For that purpose, this component imports csv file information into the database. Workflow: Not all train operators use standard journey feeds such as Hafas, VDV or Darwin. They define their schedules in different formats. One operator provides it in XML and other one in csv. To convert this journey information into RTPI standard mqtt topics, we need to develop a customized ingestion service for every customer. Dosto NEU specific workflow: For the Dosto Neu project OEBB have requested to use consist data that is retrieved through the Stadler IM SNMP interface. The CCU, using the Zabbix client will be retrieving, among other data, consist data from the Stadler IM. This data will be ingested by the RTPI server, appropriately mapped and forwarded to its consumers, FleetView and NMS. Passenger traffic should only be allowed over the trunk ports if the local CCU has gone down or is not responding. However, there will be rate limiting configured on the trunk ports of the switches, so the Passenger VLAN (Virtual LANs) does not form a bottleneck on the network and reduce the available bandwidth of other more critical VLANs. One identical client VLAN used in every consist with DHCP running on every CCU. An inter-switch configuration that by default does not allow the VLAN to pass between the consists. Under normal operation, passengers (PPPP below) would simply be using their own local CCU for internet access. In case of a CCU failure, the link towards the CCU with the lowest neighbouring CCU id in the inter-consist would be opened: in the example below CCU1 has died, meaning that the switch configuration towards CCU3 would be changed to allow the VLAN to pass, effectively putting the passengers that would normally use CCU1 inside the DHCP domain of CCU3.
